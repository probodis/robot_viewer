# Как писать release notes Telemetry Viewer

Release notes — готовый текст для Telegram о том, что изменилось для пользователей сервиса. Архивировать согласованный текст нужно в `docs/releases/<версия>.md`; для релиза frontend/backend 0.8.1 пример находится в [0.8.1.md](releases/0.8.1.md).

## Формат

Начинать с одной строки:

```text
⚡️Release Telemetry Viewer f:<версия frontend> b:<версия backend>
```

Версию frontend брать из `frontend/package.json`, backend — из `backend/app/_version.py`. Если версии различаются, указывать обе фактические версии. Далее — короткие пункты с изменениями. Сохранять простой текст, который можно скопировать в Telegram без дополнительных служебных заголовков.

## Что описывать

- Описывать итоговое поведение выпущенной версии: что исправлено, что теперь доступно и как этим пользоваться.
- Для исправления давать конкретное условие, когда возникала проблема, если это помогает понять результат. Например: машина работала без перезагрузки, заказ нового дня оказался в файле логов предыдущего дня, поэтому видео и телеметрия не открывались.
- Причину или механизм упоминать кратко, когда это объясняет исправление: используются точные ссылки на файлы из БД, а не дата имени суточного лога.
- Названия кнопок и разделов писать точно как в интерфейсе: Reload logs, Choose another log file, Find scanner archive. Рядом объяснять действие кнопки и его результат.
- Независимые изменения оформлять отдельными пунктами. Например, независимая загрузка видео/графиков и обновление только журналов — разные пользовательские действия.
- Упоминать ограничения, если они влияют на использование именно этого релиза. Не добавлять автоматически общие предупреждения или непроверенные обещания.

## Если несколько версий ещё не объявляли

Готовить один общий текст под последней выпускаемой версией. Например, если 0.8.0 не отправляли в канал, изменения 0.8.0 и 0.8.1 объединяются под `f:0.8.1 b:0.8.1`.

При объединении описывать только конечное состояние. В 0.8.0 журналы сначала загружались вручную, а в 0.8.1 автоматические вкладки вернули. В общем сообщении должно быть: «Логи автоматически загружаются внизу страницы отдельно от видео и графиков». История промежуточного решения в сообщение не входит.

Архивный файл последнего объявления должен содержать именно согласованный общий текст. Промежуточные заметки предыдущих версий не считать отдельными опубликованными объявлениями.

## Новые backend endpoints

Для endpoints этого репозитория использовать отдельный блок с точным названием сервиса:

```text
Добавлены Robot Viewer backend EP:
- GET /orders/logs (https://xapi.xrobotics.io/robot_viewer/api/v1/orders/logs?machine_id=cb-3-0007&order_id=1794011078.328) — автоматический набор журналов заказа.
```

Для каждого endpoint указывать:

1. HTTP-метод и короткий путь.
2. Полный пример URL с реальными именами параметров; значения `log_key` корректно URL-кодировать.
3. Короткое назначение endpoint. Поля ответа, коды ошибок, срок действия ссылки или формат стрима добавлять, только когда это нужно потребителю нового endpoint.

Отличать Robot Viewer backend от `xrobotics-api`: оба сервиса могут работать на одном домене, но маршруты `/robot_viewer/api/v1/...` относятся к Robot Viewer. Чтение метаданных через существующий PostgREST не является новым endpoint в `xrobotics-api`.

## Что оставить в эксплуатационной документации

Не включать в текст для Telegram подробности тестовых прогонов, staging-контейнеров, деплоя, резервных копий и внутренних коммитов. Эти сведения хранятся в [документации работы и проверки сервиса](postgrest-order-loading.md).

Не публиковать ключи, пароли, секретные заголовки и подписанные временные URL на файлы. Для примеров использовать постоянные маршруты Robot Viewer, как в согласованном тексте 0.8.1.

## Проверка перед публикацией

- Заголовок соответствует версиям выпускаемого frontend и backend.
- Все пункты описывают конечное проверенное поведение; отменённые промежуточные решения убраны.
- Названия UI-элементов совпадают с интерфейсом.
- Endpoints отнесены к правильному сервису, методы, пути и параметры проверены по коду.
- Текст в `docs/releases/<версия>.md` совпадает с согласованным сообщением для Telegram.

Эта инструкция задаёт формат документации и сама по себе не является поручением отправить сообщение в канал.
